# 结构与信息流

## 三个位置，各司其职

| 位置 | 内容 | 权威依据 |
| --- | --- | --- |
| 真实项目 | 代码、设计文件、运行数据与可交付物 | 真实文件、Git 历史与实际测试 |
| AI WorkSpace | 规则、项目目标、任务授权、结果、审查与交接 | 当前有效文件及已确认决策 |
| 人类前台 | 结论、进度、风险、下一步 | 从已验证结果提炼的摘要 |

AI WorkSpace 可以是普通文件夹；人类前台可以是 Obsidian、另一组 Markdown 文件或你已有的笔记系统。两者是否使用 Git，由你对隐私和协作的需求决定。

## 路径与项目映射

多项目使用时，可以在私有的 `PROJECT_REGISTRY.md` 中登记每个项目的真实路径、AI 上下文路径和人类摘要路径。路径属于当前机器的配置，迁移到另一台机器时要重新验证。历史记录中的旧路径应保留为历史事实，不应做全局替换。

参见空白的 [`PROJECT_REGISTRY.md`](../starter/PROJECT_REGISTRY.md)。不要把填过真实路径的注册表直接发布。

## 版本是可选的

使用版本管理的项目可增加 `CURRENT_VERSION.md`、`VERSION_HISTORY.md` 与 `RELEASES/`。当前版本由已确认的发布记录决定，不由 AI 根据聊天内容猜测。普通任务只记录版本影响；只有明确的版本或发布任务才改变版本文件。

不使用发布版本的个人项目可以跳过这一层。

## 工具交接靠文件

执行者先读取本次任务所需的少量上下文，再行动。换工具时，用 `HANDOFF.md` 指明当前状态、证据、剩余工作与边界。任何工具都不能仅凭交接文件扩大任务权限。

Skill、插件和脚本是能力来源，不是授权来源。只有任务确实需要时才加载对应能力；安装、同步与运行应各自有清楚的边界。
